# Manual accessibility checks

Static scanning is one input to an evaluation. Choose representative pages, templates, and complete user flows, including error, loading, dialog, and authenticated states. Record the URL or file, state, browser, assistive technology, steps, expected behavior, and actual evidence for each check. Browser tooling can support observation; it does not substitute for screen-reader or user testing.

Use `not-tested` for an unexecuted check and `human-review-required` where a person must decide. Keep severity independent of evidence type. A warning inferred from a source pattern must not become an automatically verified failure merely because it is severe. A `pass` is limited to the tested condition and state. Never calculate overall compliance from finding counts.

| Area | What to exercise | Evidence to retain |
| --- | --- | --- |
| Images and media | Judge alt text against image purpose; review captions, audio description, transcripts, and player controls. | The image/media and its context; the specific missing or inaccurate information. |
| Structure and headings | Inspect landmarks, heading meaning, reading order, and bypass navigation. A skipped level alone needs contextual review. | Rendered structure and accessibility-tree observations. |
| Keyboard and focus | Complete key flows using Tab, Shift+Tab, Enter, Space, and relevant widget keys; confirm visible, logical focus that is not entirely hidden by authored content and no keyboard trap. | Key sequence, focused control, and observed result. |
| Menus and dialogs | For an ARIA menu button, test Enter/Space opening and focus entering the menu, arrow-key item navigation, and Escape closing with focus returned to the trigger. For a modal dialog, verify initial focus inside, Tab/Shift+Tab containment, Escape closing, and suitable focus restoration. Ordinary disclosure navigation need not implement the ARIA menu pattern. | Widget pattern, focus before/after each action, accessible name, expanded state, and background interaction. |
| Forms | Inspect names, instructions, required fields, autocomplete, validation, error recovery, and status announcements. | Control and error association, submitted state, actual announcement. |
| Links, buttons and ARIA | Check meaningful names in context, visible-label agreement, activation behavior, roles, states, and custom widgets. | Accessible name/role/state and observed interaction. |
| Tables | Identify data versus layout tables; test header associations and complex multi-level headers. | Example cell and headers exposed by assistive technology. |
| Contrast and presentation | Measure actual rendered foreground/background combinations, including hover/focus, errors, gradients, images, transparency, and UI components. | Color pair, ratio, text size/weight or component purpose, relevant state. |
| Text resize | Enlarge text through 200%, including intermediate settings, without losing content or functionality. Record the supported browser scaling method; captions and images of text have criterion-specific exclusions. | Baseline and enlarged text, settings, and any clipped labels or unusable controls. |
| Reflow | For vertically scrolling content, test 320 CSS px width, or 400% browser zoom from a 1280 CSS px viewport. Verify no lost content/functionality or two-dimensional scrolling, except content requiring a two-dimensional layout. For horizontally scrolling content, test 256 CSS px height. | Measured CSS viewport, zoom, horizontal/vertical overflow, and justification for any exception. |
| Text spacing | Apply line height 1.5 times font size, paragraph spacing 2 times, letter spacing 0.12 times, and word spacing 0.16 times where applicable to the language/script; check for lost content or functionality. | Applied styles, affected text, clipping/overlap, and controls that stop working. |
| Motion and timing | Test pause/stop controls, time limits, and flashing risks against applicable criteria. Enable the operating system's reduced-motion preference, reload, and trigger transitions/carousels; record whether nonessential motion is reduced and tasks remain usable. | Trigger, duration, preference, and observed behavior. Reduced-motion support is an engineering recommendation; its absence alone is not proof of an AA failure. |
| Hebrew and RTL | Test language pronunciation, logical reading order, mixed-direction strings, and meaningful focus movement. | Browser and assistive-technology versions, exact text and observation. |
| Dynamic content | Trigger route changes, loading, live updates, menus, dialogs, and validation. | Before/after states, focus change, actual announcements. |
| Touch and alternative input | Review target sizes, dragging alternatives, gestures, and accessible authentication flows. | Input method, target or gesture, task result, applicable exception if any. |
| Statement | Open the actual statement; review accuracy, availability, contact route, and applicable official guidance. | Destination, observed content, unresolved questions for a qualified reviewer. |
| Real users | Test representative tasks with users with disabilities and appropriate assistive technology. | Consented observations, task barriers, and resulting remediation decisions. |

The recommended technical target is [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/). This checklist is a practical handoff, not an exhaustive criterion-by-criterion assessment. Confirm applicability and exceptions in the normative criteria. W3C provides further explanations for [text resize](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) and [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), and implementation guidance for [modal dialogs](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) and [menu buttons](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/). APG patterns are implementation guidance, not an independent legal standard. See [Israel and Hebrew guidance](israel-hebrew-rtl.md) and [the disclaimer](../DISCLAIMER.md).
